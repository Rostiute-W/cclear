# CClear 第 2 轮评审（Codex，最后一轮）

评审日期：2026-11-13。已核对 `plan-v2.md`、双方首轮评审，并只读查阅相关官方 API 文档。以下只列 v2 尚未解决或新引入的问题；不重述已采纳的保护措施。本轮未执行清理、迁移、维护或代码测试。

## 一、逐条回答 v2 第 8 节

1. **同意技术栈裁决 A。** 接受 v2 报告的工具链就绪情况作为选型依据；没有足以推翻 Tauri 2 + Rust + React/TS 的决定性理由。撤回首轮将 WPF 作为优先选项的建议。最小 capabilities 的具体实现仍需修正，见 P1-04。
2. **反对直接批准当前 safe 清单。** 通用 Temp 即使超过 7 天且未检出占用，也不具备可再生证明，应退出一键清理。其余明确的浏览器/着色器/缩略图缓存可作为 safe 候选，但材料未展示逐规则验证结果；不能仅因本机路径存在就标为“已验证”。见 P0-01、P0-05。
3. **反对把 §2.3 的判定当作可靠删除依据。** 最高版本、非当前 commit、旧文件名、未注册 VHDX，都不足以证明无用。允许继续只读标出候选，不能据此默认获得隔离资格。见 P0-02、P0-03。
4. **反对“首轮 P0 已全部解决”的判断。** Temp 资格判断仍未解决；新增的版本淘汰、应用存储直删、回收站与冻结清单冲突，以及锁检测保证过强，仍会影响数据安全。具体修改如下。
5. **同意整体里程碑顺序，反对 M1 将全量锁检测作为首屏前置条件。** Top N、候选和扫描完整性先展示；锁检测按选中项异步查询，环境卡可随后加载。M2 之前必须完成删除竞态验证；M3 的诊断数据恢复类型要先明确，若默认隔离则延至 M4。M4 仅上线已证明失效的 leftover 子规则，其余保持只读；无需等待 M6 才交付实用版本。

## 二、剩余问题与具体修改

### P0：相关破坏性能力开放前必须解决

**P0-01｜§2.1：7 天是筛选条件，不是安全证明。**

首轮提出的核心问题仍在：应用可能关闭数周后再次使用 Temp 中的文件，创建/修改时间和锁检测都不能证明可再生。改为通用 Temp 属于 caution、默认不选，保留 7 天筛选并明确永久删除；只有已验证用途的具体缓存子规则可以升为 safe。空目录仅在本次明确批准的子树内、确认真正为空后删除，不能顺带清掉 Temp 下未被选择的结构。

**P0-02｜§2.3：“保留最新版”会淘汰仍被引用的版本。**

WPS 插件、MathWorks ServiceHost、VS Code/Cursor 扩展可能存在版本绑定、固定旧版或回滚需求；Code.exe 的版本资源也不必然标识每个目录对应的 commit。隔离会立即移除源目录，不能以“能恢复”替代失效判定。

具体改法：取消 WPS/MathWorks/扩展的通用“只留最新”执行规则；无法从产品的实际加载清单、安装配置和更新状态证明废弃时归 manual。VS Code 按对应版本安装布局核对启动目标与匹配的 `product.json`，同时排除未完成更新和回滚保留项；证据冲突即跳过。`.obsolete` 只能在确认其格式/所属安装及所有相关实例退出后作为较强候选证据；`.<guid>`、`.previous-*`、`*.old-*`、超过一天的安装目录均不得仅凭名称或年龄判废弃。用户 bin 规则收窄到已适配产品及其更新协议，不匹配任意 `*.old-*`。

**P0-03｜§2.3：未注册 VHDX 不能归“孤立垃圾”。**

未出现在当前用户 Lxss 注册项，只能证明这次查询未找到关联；它可能是备份、待恢复发行版或其他挂载用途，里面仍可能有唯一数据。`wsl --list` 列出发行版，不是“不在运行”的判据；运行筛选应使用 `--running`，但停机也不等于可以删除。[WSL 官方命令说明](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)

将该规则改名为“未关联虚拟磁盘”，移至 manual，排除在 leftover 批量隔离和到期清空之外。用户核实归属与备份价值后，可走独立的大文件迁移流程；仅核对注册表、年龄、运行状态不授予删除资格。

**P0-04｜§2.2/§3：caution 不等于可再生，恢复枚举不能完整表达现有规则。**

`Service Worker\CacheStorage` 是站点管理的持久存储，不保证只是可重新下载的 HTTP 缓存；浏览器提供的 Cache API 能保存应用构造的响应。[Chrome 官方示例](https://developer.chrome.com/docs/ai/cache-models) 因此先改为站点存储管理引导，不能整批按 regenerable 直删；ScriptCache 与之拆开验证。

引用 AGY 路径表时，`xwechat_files\*\cache/temp`、钉钉 `Temp/xcdn`、WPS `wps\download`、`office6\update` 等也没有随表附上用途验证证据。版本识别只能确认布局，不能补足语义证据：这些项先保留分析候选，验证后才赋予执行动作。各类 log/Crashpad 统一走诊断策略，不能因为来自“应用缓存表”绕过 30 天筛选。

为诊断文件和回收站增加明确的 `irreversible_file`（或等价明确动作）及逐项永久删除确认；不愿直删的诊断数据用 quarantine 并延至 M4。当前三个 recovery 值无法表达不可再生的文件永久删除，不能错标 regenerable。30 天只决定候选，不决定恢复性。

**P0-05｜§2.1/§6：Restart Manager 不能证明持续无写入者。**

它查询已注册资源的当前使用情况；不是目录递归查锁或未来写入屏障。把目录路径直接注册后查询还可能返回拒绝访问。[RmGetList 文档](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmgetlist)

把 UI 的“确认无锁”改为“本次未发现占用/检测不完整”。仅对已枚举的具体资源检测，错误不得等同空列表。safe 执行时再次检查应用状态与文件身份，应用重启则停止相关规则。迁移须有可验证的停止写入条件，并验证源在复制、校验、切换间未变化；无法维持一致性则保留源并中止，不能靠最后一次 RM 查询放行。加入复制中改写、应用重开、只改内容而保持长度的失败用例。

**P0-06｜§5：句柄方案方向正确，但 API 描述尚未证明消除了竞态。**

仅“打开父目录 + FILE_FLAG_OPEN_REPARSE_POINT”不会自动让之后的按路径删除变成相对父句柄操作。必须写明对象打开、身份复核、删除使用的是同一受约束对象，不能校验完再交给 `remove_dir_all` 等按字符串递归处理。

M2 前验证具体方案，例如逐组件以父句柄相对打开子项，拒绝重解析点，核对文件身份后按句柄删除；Windows 的 [NtCreateFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile) 提供相关相对打开机制，但仍须验证祖先改名/移出边界的约束。以实际竞态测试通过作为准入条件，不能仅检查 API 标志出现。发现禁止子项或新文件时保留父目录，不能让整目录隔离/删除绕过逐项禁区和冻结清单。

**P0-07｜§2.2/§3：整盘清空回收站与“只执行冻结清单”冲突。**

限定 C 卷解决了跨盘问题，但若最终使用 [SHEmptyRecycleBinW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shemptyrecyclebinw)，清空的是执行时该卷的回收站，预览后刚进入的文件也可能被清掉。

首版改为按已确认的 Shell 条目标识逐项删除并复核，新增条目保留；如果暂时只能整卷清空，则退出冻结清单执行器，做独立的“清空执行时 C 盘回收站全部内容”确认，不能声称只处理预览内容。两种语义必须选定，不能共用模糊按钮。

### P1：首版应补齐的准确性与边界

**P1-01｜§3：隔离目标选择和容量公式仍不闭合。**

“剩余空间最大的固定 NTFS 卷”可能选中 C 本身；应按卷身份排除源卷、同步根、源目录后代及既有隔离区的循环目标，执行前展示目标并允许更改。“待隔离量”应按目标复制策略计算最坏新增占用，不能直接用源 AllocationSize：稀疏/压缩文件、硬链接展开会膨胀。无法保证这些特性时拒绝该对象或按展开体积预留，并在复制中监测空间；固定加 2 GB 不能代替此计算。保真、权限与崩溃恢复要求明确同样适用于隔离事务，不能仅以主数据流哈希相等验收。

**P1-02｜§2.2：官方命令分类与超时继承有误。**

`cargo cache` 通常指第三方 [cargo-cache](https://github.com/matthiaskrgr/cargo-cache)，不能直接列为 Cargo 官方清理命令；默认调用也不是明确的清理计划。首版改为只展示，后续若适配需锁定来源、版本与精确子命令。NuGet 的 [`all --clear`](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-nuget-locals) 包括全局包存储，须拆分作用域并展示实际路径，不能仅标“下载缓存”。

不要整体继承 AGY 的统一 60 秒超时：缓存命令可能等待工具自己的锁。超时先报告状态、停止派发后续动作；不把“等待超时”视为已取消或据此强杀进程。退出/取消行为按每种命令验证。

**P1-03｜§5：全面拒绝 `\\?\` 与长路径支持矛盾。**

区分外部输入与内部规范表示：可拒绝用户提交的任意设备命名空间，但内部支持经验证的扩展长度 DOS 路径，且仍校验卷身份和重解析点。8.3 路径应按对象身份归一后验证，不能只靠字符串规则判绕过。补一个超过 260 字符的合法文件与同样长度的越界负例；不支持的情况明确展示，不静默遗漏。

**P1-04｜§0/M0：最小 capabilities 不会自动限制所有自定义命令。**

Tauri 文档说明，默认注册的应用命令可供各窗口/WebView 使用，需通过 `AppManifest::commands` 纳入权限控制并配套授权。[Tauri Capabilities](https://v2.tauri.app/security/capabilities/) M0 增加可验收条件：未授权窗口/来源无法调用执行命令；禁止远程页面获清理权限；前端仅传已确认计划 ID 和选择项，由 Rust 持有实际执行清单。只关闭 fs/shell 插件不足以完成这一边界。

**P1-05｜§6：官方配置迁移缺少实际数据迁移/重建的判定。**

“写用户级配置 → 新进程验证”可能只是换了空缓存位置；也不能覆盖项目配置、CLI 参数及旧 IDE 环境。给每个工具明确选择“迁移旧缓存”或“允许重建”，记录有效配置来源；先验证新位置能完成对应工具操作，再检查旧位置不再被使用，最后单独确认清理旧副本。解析出的有效缓存不在 C 卷时，退出 C 盘清理任务，不顺带清另一卷。

### P2：文档收口

**P2-01｜§1 与继承说明：约 10 GB 是候选体积，不是已证实收益。**

改为“待核实候选约 10 GB”，排除未证明失效的版本与虚拟磁盘后重新汇总。实施前增加一张最终规则表，明确“等级、恢复方式、资格证据、执行阶段”：当前引用 AGY 应用表可能把 WPS 多版本规则同时放入 caution 与 leftover；Package Cache 在 §0 永不清理、§2.4 manual 又共享可迁移动作。分别指定唯一规则和动作集合。v1 的用户自定义命令也应明确首版禁用，避免靠“未被推翻继续有效”引回动态删除入口。

## 三、最终意见

**同意进入 M0/M1；不同意按现有资格规则直接开放 M2–M4 的破坏性操作。** 将上述 P0 逐条改成准入条件即可推进实现，不需要再扩大清理范围或增加一轮选型讨论。本轮只验证了文档与官方 API 语义，未验证任何删除、复制或恢复实现。
