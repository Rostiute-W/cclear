## 目标
修复检查点 C 审查发现的问题：命令类规则拖慢全部规则评估、清空回收站可能没有日志、缓存“是否在 C 盘”只看盘符、命令执行之间没有互斥，以及两处前端格式错乱。

## 实现要点

### A. 全部规则评估回到 3 秒以内（P1）
实测：`evaluate_all` 首次运行 11.5 秒，之后 5.3 和 5.5 秒；去掉 7 条命令类规则后，其余 61 条规则跨规则并行只要 2.1 秒。慢在 `rules/commands.rs` 的 `dir_size`：它单线程递归，而 `command-uv-cache` 和 `command-uv-cache-clean` 指向同一个 uv 缓存目录（81,039 个文件），这个目录被完整统计了两遍（1.8 秒和 4.1 秒）。工具查询本身不慢（npm、pip、dotnet 每个约 0.1 到 0.4 秒）。
1. 删除 `commands::dir_size`。缓存大小改用 `rules/resolve.rs` 现有的并行枚举（`collect_all`/`collect_tree`，可以新增一个 `pub(crate)` 包装函数），把缓存路径当作锚点，用不带年龄过滤和排除项的 AllContents 选择器。这样统计口径就和文件类规则一致：rayon 并行，跳过 reparse 目录和文件，`classify_file` 处理云占位符，硬链接按“卷序列号 + 文件 ID”去重。
2. 同一次 `evaluate_all` 中，同一个缓存路径只统计一次（路径比较不区分大小写，pip 报出的是小写的 `c:\users\...`）。实现方式自定，例如先并行查询所有命令规则的缓存路径，去重后统计，再分发给各条规则。单独调用 `evaluate(rule, ...)` 的行为不变。
3. 这一条不写测试，由 Droid 用真实数据复测。验收口径：在新进程中运行 `evaluate_all`，第 2、3 次（热缓存）都 ≤3 秒，首次耗时如实报告。

### B. 清空回收站前先打开日志（P2）
4. `src-tauri/src/commands/recycle.rs` 的 `recycle_bin_empty`：先打开 `FileJournal`，打不开就直接返回“操作日志无法写入，未清空回收站：<原因>”，不清空回收站。打开成功后再查询、比对、清空、写 `SpecialAction`。

### C. 按缓存路径本身所在的卷判断是否在 C 盘（P2）
5. `win/volume.rs` 的 `path_volume_serial` 现在只打开盘符根目录。如果 C 盘上的缓存目录其实是指向 D 盘的 junction，它会被当成在 C 盘。改为：路径存在时，打开路径本身（跟随链接，不加 `FILE_FLAG_OPEN_REPARSE_POINT`，带 `FILE_FLAG_BACKUP_SEMANTICS`，只申请读属性），读取最终所在卷的序列号；路径不存在时，向上找最近一个存在的祖先目录，按同样方式读取。`rules/commands.rs` 中 `drive_check` 的注释按实际行为改写。
6. 不写测试（临时目录无法造出跨卷 junction），由 Droid 审查代码。

### D. 命令执行和回收站与清单执行互斥（P2）
7. `command_execute` 和 `recycle_bin_empty` 都使用 `AppState` 现有的 `start_exec()`/`finish_exec()` 锁，和 `plan_execute` 共用：同一时间只允许一次清理类操作。已经有操作在进行时，返回“已经有一次清理在进行，请等待结束或先取消”。无论成功、失败还是 panic，结束后都要调用 `finish_exec()`。
8. 命令超时返回后就释放锁。结果里已经说明“进程可能还在运行”，不需要额外处理。
9. 清理页：任意一条命令、回收站或清单正在执行时，其他“运行”“清空回收站”“一键清理安全项”“清理选中项”按钮都禁用，并以后端的报错为准。

### E. 前端格式（P2）
10. `src/api.ts` 中 `}export function defaultScanRoots` 拆回两行。`src/pages/History.tsx` 中 `function ruleSummary(...): string {  if (plan.rules.length === 0) {` 拆回两行。同时检查本次改动的文件里有没有其他两行粘在一起的地方。
